================================================================================
  3. ARMADILHA CRÍTICA DE PERMISSÕES (importante!)
================================================================================

Este tenant tem a configuração de segurança interna do PWA QUEBRADA:

  - A UI de admin "PWA Settings > Security > Manage Groups" retorna HTTP 500
  - Os grupos SharePoint ("Administradores para o Project Web App" etc.) NÃO
    estão vinculados aos grupos de segurança internos do Project Server
  - Resultado: mesmo um admin SharePoint só recebe duas permissões PWA:
        Projects.Add  e  Resources.Add
  - PSI SOAP (/_vti_bin/PSI/*) responde 401 "Attempted unauthorized operation"
  - /_api/ProjectData/* (OData reporting) responde 403 GeneralSecurityAccessDenied
  - /_api/ProjectServer/Projects('id')/Tasks responde 404 "This project either
    does not exist..."

O que NÃO funciona neste tenant:
  ✗ /_api/ProjectData/Tasks                  → 403
  ✗ /_api/ProjectData/Assignments            → 403
  ✗ /_api/ProjectData/Resources              → 403
  ✗ /_api/ProjectServer/Projects(id)/Tasks   → 404
  ✗ /_api/ProjectServer/Projects(id)/Draft   → 404 (subresources)
  ✗ /_api/ProjectServer/ProjectResources     → 403
  ✗ /_api/ProjectServer/SecurityGroups       → 404
  ✗ /_vti_bin/PSI/*.asmx                     → 401
  ✗ PWA admin .aspx pages                    → 401 (precisam de cookie)


================================================================================
  4. A DESCOBERTA QUE DESTRAVOU TUDO
================================================================================

Embora /Projects(id)/Tasks retorne 404, fazer um filter+expand na LISTA
contorna a checagem de permissão e devolve as tarefas:

   FUNCIONA:
   GET /_api/ProjectServer/Projects?
       $filter=Id eq guid'<PROJECT_ID>'
       &$expand=Tasks,Tasks/Assignments,Tasks/Assignments/Resource

   NÃO funciona:
   GET /_api/ProjectServer/Projects('<PROJECT_ID>')/Tasks

Esse mesmo padrão (filter+expand na lista) destravou:
  - Tasks
  - Assignments
  - Custom field values (via Draft/IncludeCustomFields)
  - Resource names (via Tasks/Assignments/Resource)


================================================================================
  5. LIMITES DA API DESCOBERTOS
================================================================================

5.1 — $expand com sub-coleções: limite de 20 projetos por request.
      Acima disso retorna 500 "Too many projects: 27. You cannot load
      dependent objects for more than 20 projects."
      SOLUÇÃO: batches de 15 projetos com filter OR.

5.2 — $select dentro de $expand: NÃO SUPORTADO.
      Tentativa: $expand=Tasks($select=Id,Name) → HTTP 400
      Tem que aceitar TODOS os campos do expand.

5.3 — $filter aninhado em coleções: NÃO SUPORTADO.
      Tentativa: $filter=CustomFields/LookupEntries/Id eq guid'...' → HTTP 400

5.4 — _get_all sem $top falha em coleções com expand.
      Sempre passe $top=200 (ou maior que o total esperado).

5.5 — A pagina raiz /_api/ProjectServer (sem ID) FUNCIONA e lista todas
      as coleções disponíveis no servidor.


================================================================================
  6. AUTENTICAÇÃO MSAL (device flow)
================================================================================

Scope:    ["https://horizontesarq.sharepoint.com/AllSites.Read"]
Authority: https://login.microsoftonline.com/<TENANT_ID>

Fluxo:
  1. app.initiate_device_flow(scopes=SCOPES)
     → retorna { user_code, verification_uri }
  2. Usuário abre https://login.microsoft.com/device e digita o código
  3. Faz login normal (com MFA se exigido)
  4. app.acquire_token_by_device_flow(flow) devolve o token

O token vem com:
  - access_token (válido por ~1h)
  - refresh_token (válido por 90 dias)

A biblioteca MSAL cuida da renovação silenciosa.
O cache fica em .token_cache.json (NÃO COMMITAR).

Importante: após mudança de grupo de segurança no SharePoint, o token
antigo ainda reflete a membership antiga. Tem que apagar o cache e
re-autenticar (pwa_client.logout() + start_device_flow()).

================================================================================
  9. CAMPOS DE TAREFA DISPONÍVEIS VIA $expand=Tasks
================================================================================

Ao expandir Tasks na lista de projetos, cada task vem com ~150 campos.
Os úteis para nós:

  Id, Name                                    → identificação
  OutlineLevel, OutlinePosition               → hierarquia
  IsSummary, IsMilestone, IsProjectSummary    → tipo
  Start, Finish                               → datas reais (ScheduledStart/Finish)
  ActualStart, ActualFinish                   → datas executadas
  BaselineStart, BaselineFinish               → linha de base
  Duration                                    → "57d" / "11dd" (string formatada)
  DurationMilliseconds                        → 1641600000 (NÃO USAR — ver abaixo)
  BaselineDurationMilliseconds                → idem para BL
  PercentComplete                             → 0..100
  Work, ActualWork, RemainingWork             → horas (string "1.080h")
  WorkBreakdownStructure                      → WBS "1.2.3"

DURAÇÃO: LER `Duration`, NUNCA `DurationMilliseconds`
-----------------------------------------------------
`Duration` é a string formatada e é a única fonte da duração no coletor. Traz o
número e a unidade juntos, na grafia pt-BR do Project:

    "18d"      → 18 dias ÚTEIS
    "11dd"     → 11 dias CORRIDOS (decorridos; o "ed" do Project em inglês)
    "33,38dd"  → fracionada, vírgula decimal

Levantamento de 26/08/26 nas 5794 tarefas dos 13 projetos do PWA: `Duration`
nunca vem nulo nem vazio, e os únicos sufixos que ocorrem são `d` (4341) e `dd`
(1453) — este tenant é todo pt-BR. Nenhuma tarefa em horas, semanas ou meses.
São 107 com casa decimal. As 28 com `IsDurationEstimate` NÃO ganham o "?" que o
Project mostra na tela; a string do REST vem limpa.

`DurationMilliseconds` foi abandonado por dois defeitos:

1. Não diz a unidade. A espécie tinha de ser adivinhada comparando o número com
   o vão do calendário (`duracao == 3 * vão`).
2. É int32 e ESTOURA. Acima de 74,6 dias úteis (ou 24,9 corridos) o servidor
   devolve -2147483648, que o coletor tratava como duração zero: eram 435
   tarefas nos snapshots, e no comparador cada uma passava como "não mudou de
   duração" sem que nada aparecesse no report.

No snapshot a duração vira três campos:

    duracao      → int, JÁ ARREDONDADO, na unidade da própria tarefa (18, 11)
    duracaoUn    → "util" | "corrido"
    duracaoTxt   → a grafia do Project ("33,38dd"), para a tela de saúde

`duracaoUn` é o MARCADOR DE FORMATO. Sem ele o dado veio de coleta anterior a
26/08/26, em que `duracao` contava unidades de 8h e um dia corrido valia 3 —
escala diferente, que não se compara com a de hoje. Quem consome checa
`duracaoUn`, nunca `duracao` sozinho. O fetcher recoleta qualquer snapshot sem o
campo, mesmo sem republicação (fetcher._formato_atual).

Arredondamento: meio dia SOBE (floor(v + 0,5)), e não o round() do Python, que
arredonda 2,5 para 2. Marco continua sendo duração zero testada no valor EXATO,
antes de arredondar — "0,2d" arredonda para zero e viraria marco sem ser.

Para dias corridos (calendário): diferença em dias entre Start e Finish. É outra
medida, e não substitui a duração — ver a seção do comparador.


================================================================================
  10. NOMES DOS RECURSOS POR TAREFA
================================================================================

Não precisa fazer fetch separado de ProjectResources (que dá 403).
Usar nested expand de 3 níveis:

  $expand=Tasks,Tasks/Assignments,Tasks/Assignments/Resource

Cada Task vem com Assignments[].Resource.Name preenchido.

Aviso: a Task SUMMARY (a primeira, OutlineLevel=1) tem 0 assignments.
Os recursos aparecem só nas tasks folha (não-summary).


================================================================================
  11. % PREVISTO
================================================================================

Não é exposto pela API. CALCULADO por fórmula clássica MS Project:

  ref_start = baseline_start OR actual_start OR project_start
  ref_end   = baseline_end   OR actual_end   OR project_end

  Se hoje < ref_start: 0%
  Se hoje > ref_end:   100%
  Senão: (hoje - ref_start) / (ref_end - ref_start) * 100

BARRA DE PROGRESSO DO BOTÃO "ATUALIZAR"
---------------------------------------
O fetcher publica o andamento em data/fetch_progress.json a cada avanço, e o
dashboard desenha uma faixa de 3 px sob o botão.

  {run_id, fase, rotulo, feito, total, ativo, atualizado_em}

  - fase: iniciando → autenticando → projetos → tarefas → limpeza → concluido
          (ou erro). Só a fase `tarefas` tem denominador: o número de projetos
          a coletar. Nas outras, total = 0 e a barra fica indeterminada.
  - O denominador são os projetos A COLETAR, não todos: os reaproveitados do
    snapshot entram como nota no rótulo. Barra sobre o trabalho que existe.
  - run_id: POST /api/refresh gera o identificador, grava o andamento inicial
    (o processo demora a subir) e passa `--run-id` ao fetcher. O browser só
    aceita andamento com esse id — sobra de coleta anterior é ignorada.
  - GET /api/progress devolve o arquivo. O browser pesquisa a cada 1 s e desiste
    se nada mudar por 3 min (fetcher travado ou morto).
  - Andamento é acessório: falha ao gravá-lo nunca interrompe a coleta.

COLETA INCREMENTAL
------------------
A lista de projetos é sempre atualizada (é barata e traz o LastPublishedDate de
todos). As tarefas — o grosso do tempo — só são buscadas nos projetos
republicados desde a última coleta bem-sucedida.

  - O carimbo da comparação é `publicadoEm` (LastPublishedDate COM hora, para
    distinguir duas publicações no mesmo dia). `ultimaPublicacao`, só data,
    continua sendo o campo exibido na tela.
  - data/fetch_state.json guarda a publicação EFETIVAMENTE coletada de cada
    projeto. É separado do projects.json de propósito: aquele é sobrescrito a
    cada run mesmo quando a coleta das tarefas falha; o estado só avança quando
    o tasks_<pid>.json foi gravado, então falha é retentada no run seguinte.
  - Projeto sem carimbo de publicação é sempre coletado (na dúvida, coleta).
  - `python fetcher.py --full` força a recoleta de todos.

Duas outras economias no mesmo caminho:

  - fetch_tasks usa $select com os 11 campos realmente consumidos. Sem ele o
    servidor devolvia a entidade inteira de cada tarefa e de cada atribuição.
    Se o servidor recusar os caminhos aninhados (HTTP 400/404/500), o cliente
    registra um WARNING e segue sem $select pelo resto do processo.
  - As tabelas de pesquisa (Cliente/Cidade/Coordenador) vão para
    data/lookup_cache.json com validade de 7 dias, em vez de serem baixadas a
    cada processo. Entry desconhecida força uma recarga, uma vez por processo.

              ↓
   ┌──────────────────────────────┐
   │ app.py serve da memória/disco │

A REGRA QUE DEFINE TUDO
-----------------------
O comparativo tem exatamente DOIS lados: o cronograma de agora e o cronograma de
quando o ultimo report foi gerado. Nao existe terceira data. Publicacao de
cronograma que nao virou report nao e comparada com nada e nao e guardada.

Disso decorre que nao ha historico a manter: ha UM estado por projeto,
substituido a cada report SALVO no historico.

Salvo, e nao gerado: a tela do relatorio tem um toggle "Salvar no historico"
(ligado por padrao) que decide se aquele report entra na historia do projeto. E
um interruptor no formato do iOS — trilho verde ligado, vermelho desligado, com
o botao redondo deslizando entre os dois: ali nao ha acao a executar, ha um
estado que precisa ser lido de relance.
Nem todo report e de rotina — ha o tirado para conferir uma duvida, para uma
reuniao fora de epoca, para testar uma correcao do cronograma —, e um report
desses, se salvasse a base, engoliria o periodo do proximo. Desligado, a base
fica como estava e o proximo comparativo parte do ultimo report SALVO.

  * Houve um historico.py com 15 versoes em "base completa + deltas", retencao
    com dobra do delta antigo na base, reconstrucao por data (versao_em) e
    hierarquia por parentId para nao reescrever indices. Tudo aquilo existia
    para responder "como era o cronograma numa data qualquer" — pergunta que o
    report nao faz. Foi apagado junto com os data/history_*.json.

BASE DO REPORT (report_base.py)
-------------------------------
data/report_base_<pid>.json, gravado por POST /api/report-base quando o usuario
fecha a tela do report com o toggle ligado. Guarda CINCO campos por tarefa: id,
start, end, duracao, duracaoUn.

  - Sao os unicos que o lado antigo da comparacao e lido para dar: o pareamento
    e por id e a variacao e de datas e de duracao. Nome, recurso, nivel e
    hierarquia saem sempre do cronograma ATUAL, que e quem escreve o rotulo de
    cada linha.
  - A duracao entrou em duas etapas. Em 25/08/26 como numero solto, e em
    26/08/26 com `duracaoUn`, quando ela passou a sair do campo Duracao do
    Project. `duracaoUn` e o MARCADOR DE FORMATO da base: sem ele o numero
    guardado esta na escala velha (unidades de 8h, um dia corrido valendo 3) e
    nao se compara com o de hoje.
  - Base velha nao e convertida nem estimada por outro caminho — o comparador
    declara a duracao indisponivel e IMPRIME A RESSALVA no report. Cada base se
    corrige sozinha no proximo report salvo. Nao ha migracao a rodar: as 13
    bases no disco em 26/08/26 sao todas do formato antigo.
  - A ordem da lista importa: o primeiro item e a tarefa-resumo do projeto
    (nivel 0), de onde saem o termino e a duracao totais.
  - `publicadoEm` (LastPublishedDate COM hora) carimba a base e vira a data do
    titulo da secao. `geradoEm` e o instante da geracao, usado so como fallback.
  - API inteira: carregar(), gravar(), data(). Tres funcoes.

  GRAVAR E DEPOIS DE MONTAR O RELATORIO, nunca antes: base gravada num report
  que falhou ao ser montado engoliria o periodo seguinte. Hoje a geracao nao

COMPARADOR (comparador/)
------------------------
Os dois lados sao data/report_base_<pid>.json e data/tasks_<pid>.json. Ambos tem
GUID de tarefa, entao o pareamento e por id.

  comparador.secao_desde_base(base, tarefas_atuais) -> markdown

Renomear tarefa NAO quebra a comparacao. Conferido com as "Analise" do Vila

COMO O COMPARATIVO CHEGA NA TELA
--------------------------------
    index.html (form-report)
      -> POST /api/report-json {project_id, nome_projeto}
           app._secao_comparativa()      -> report_base.carregar()
                                         -> comparador.secao_desde_base()
           Report.gerar_relatorio_web_json(tarefas, nome, secao)
           app._BASE_PENDENTE[pid] = ... <- o cronograma de agora fica pendente
      <- {content, filename, comparativo:{desde | aviso}}

    modal do relatorio (toggle "Salvar no historico", ligado por padrao)
      -> ao fechar: POST /api/report-base {project_id, salvar}
           salvar=true  -> report_base.gravar()  <- vira a base do proximo
           salvar=false -> pendencia descartada  <- report temporario
      <- {success, salvo}

  A pendencia e consumida nos dois casos: a decisao e tomada uma vez. Fechar sem
  pendencia (409) so acontece se o servidor tiver reiniciado com o modal aberto.

  Nao ha seletor de data na tela nem parametro de data na rota: nao existe o que
  escolher, ha uma base so. Houve um seletor "Comparar com" e um GET
  /api/versoes/<pid> enquanto o modelo era de historico; sairam junto com ele.

  Comparativo e acessorio: se ele falhar, o report sai sem a secao e o aviso vai
  em `comparativo.aviso` — nunca deixa o usuario sem relatorio.

POR QUE NAO HA CALCULO DE CAMINHO CRITICO
-----------------------------------------
Medido nos 17 cronogramas: as tarefas-folha criticas cobrem 3% a 17% do prazo na
maioria dos casos (Vila Gilda 8%, Brasilandia 3%); a UBS Santa Rita nao tem
nenhuma; e andar do termino para tras pelos vinculos percorre a cadeia inteira
em apenas 7 dos 17 projetos.

O motivo e que esses cronogramas sao ancorados por data contratual: o marco
final e fixo, entao quase tudo antes dele tem folga. Atribuir dias "ao longo da
cadeia critica" produziria numeros que parecem precisos e nao sao.

O QUE FUNCIONA: A CADEIA DE VINCULOS
------------------------------------
A cobertura de vinculos e alta (89-100% das folhas tem predecessora) e a
aderencia tambem (86-100% dos FS coerentes com as datas). rede.py caminha do
termino do projeto para tras, seguindo em cada passo a predecessora cujo
deslocamento explica o da sucessora (empurrador()), e coleta quem AUMENTOU A
DURACAO no caminho.

Ofensor e quem aumentou a duracao dentro dessa cadeia. Tarefa que so foi
deslocada por inteiro herdou o atraso, nao o produziu. Marco (duracao zero)
nunca e ofensor: empurrador() pula por cima dele para apontar a causa real.

Tolerancia: datas sao de calendario e vinculos sao em dias uteis, entao o
casamento de deslocamentos usa folga de 3 dias (rede.TOL_DIAS).

DURACAO E O CAMPO DURACAO DO PROJECT, NAO O VAO ENTRE AS DATAS (25/08/26)
------------------------------------------------------------------------
Ate 25/08/26 o aumento de duracao era `(fim-inicio) atual - (fim-inicio) antigo`,
em dias de calendario. Bastava a tarefa escorregar para cima de um fim de semana
ou de um feriado para virar ofensora sem ter esticado um dia. No 2525 o report
de 25/08 acusou tres ofensores e dois eram isso: `URBANISMO / 2291GG-A-500029 /

dias uteis dos dois lados, +2 corridos porque o Finados empurrou o inicio para
terca e o vao passou a engolir o sabado e o domingo).

Contar dia util no lugar do calendario nao resolve: FAZ O ERRO SIMETRICO. O
Project agenda cada tarefa numa de duas unidades e as duas convivem no mesmo
cronograma — nas 689 folhas com duracao do 2525 sao 374 em dias uteis e 312 em
dias corridos (todas as `Analise`, lancadas como edays). Uma `Analise` de 10
edays nao muda de duracao quando a janela muda de lugar, mas o numero de dias
uteis dentro dela muda: a `Analise 01` do 2291GG-G-500002 iria de 6 para 9 e
apareceria como ofensora de +3. Alem disso, contar dia util exigiria uma tabela
de feriados que nunca vai bater com o calendario do Project.

O que resolve e comparar o proprio campo Duracao. A subtracao e exata para as
duas especies de tarefa e nao consulta calendario nenhum. Quem faz e
comparador._variacao_duracao().

A primeira versao disto (25/08/26) adivinhava a especie pelo numero, testando

O SCORE E UMA TAXA, NAO UMA CONTAGEM
------------------------------------
nota = 100 * (1 - taxa/limite), com taxa = tarefas com o defeito / tarefas-folha.
Sem isso o Sede 2 (2.286 folhas) seria sempre pior que o Jardim Coreano (19), o
que diria mais sobre o tamanho do projeto do que sobre a qualidade dele. O score
final e a media das notas ponderada pelos pesos.

  KPI                              peso  limite   o que conta
  Dependencias ligadas a resumo      30    10%    pred e resumo, ou resumo com pred
  Tarefas sem sucessora              20    25%    tarefa que nao empurra ninguem
  Tarefas sem predecessora           15    25%    tarefa sem nada antes
  Tarefas nivel 4 sem recurso        10    10%    nivel 4, fora marcos, sem recurso
  Marcos com duracao                 10     5%    IsMilestone com duracao > 0
  Duracoes fracionadas                5     5%    duracao com casa decimal
  Trabalho fora do nivel 4           10    30%    trabalho em nivel != 4, fora marcos

Faixas: 90 Excelente · 75 Bom · 60 Regular · 40 Ruim · abaixo disso Critico.

A UNIDADE DA LINHA E O LOTE, NAO O DOCUMENTO

Documentos da mesma disciplina que andam na mesma revisao e nas mesmas datas

A VERSAO DE E-MAIL SAI DO PYTHON, NAO DO BROWSER
------------------------------------------------
O corpo do e-mail no Outlook e o editor do Word, e colar HTML nele nao e abrir
uma pagina: o Word remonta tudo. Por isso o HTML do e-mail nao reaproveita nada
do CSS da tela — sao duas linguagens diferentes, e manter as duas no mesmo
modulo evita que uma mude sem a outra.

O primeiro desenho (um <div> de titulo e uma tabela por iniciativa) saiu
desmontado quando colado de verdade no Word. Refeito em 11/09/26 com regras
tiradas de cada defeito visto:
  - UMA tabela so, 640 px, com a largura de cada coluna fixa. Tabelas separadas
    saem cada uma com as colunas numa largura e o e-mail perde o alinhamento.
  - Fonte declarada em CADA celula: o Word nao leva o font-family de um <div>
    para dentro da tabela.
  - Nada de margem ou borda em <div>, que some. Respiro e linha de altura fixa;
    a faixa da iniciativa e bgcolor na celula.
  - Maiuscula escrita no texto; nada de letter-spacing ou text-transform.
  - Um codigo de documento por linha: na mesma linha o Word quebra o codigo no
    hifen.
  - Cinza nunca mais claro que #6b7280 — o #94a3b8 sumia.
  - Cabecalho uma vez so, no topo. Disciplina com o mesmo nome da iniciativa nao
    aparece, porque so repetiria a faixa logo acima.
No topo, um resumo: documentos, em andamento, a iniciar.

Como conferir sem Outlook: por o HTML no clipboard como CF_HTML (o formato que
o Chrome grava), colar num documento do Word via COM e exportar a pagina
(Pages(n).EnhMetaFileBits → PNG). E o mesmo motor que monta o corpo do e-mail.

O e-mail sai sempre COMPLETO, com todos os codigos de documento e independente do
filtro de situacao da tela: o fornecedor precisa da lista inteira dele, nao do
recorte que o PMO esta olhando.

A tela copia com navigator.clipboard.write (text/html + text/plain) e cai para
execCommand('copy') sobre um div contentEditable oculto se o browser recusar.

Dentro do card e tudo escala de cinza — a hierarquia sai do peso do texto
